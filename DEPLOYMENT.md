# Deployment

Three pieces, three providers. They're independent — each is reachable from the
others over the network.

```
Netlify  ──  frontend (static build of frontend/)
Render   ──  FastAPI API           ──DATABASE_URL──▶  Neon (Postgres)
```

## Why not Netlify for all of it

Netlify's compute is Functions and Edge Functions, which run JavaScript/TypeScript
and Go — there's no runtime for a long-lived Python ASGI process, so FastAPI
can't run there.

Netlify DB can't be used either, despite being Postgres. Its documented access
surface is *Functions, Edge Functions, Builds, and Agent Runners*, and
production deploys are the only context permitted to reach the main database.
An external Render service isn't a deploy context, so there's no seam to connect
through. Hence Neon directly, which hands out an ordinary connection string.

---

## 1. Database — Neon

1. Create a project at neon.tech and copy the connection string.
2. Rewrite the scheme so SQLAlchemy selects the installed driver, and keep SSL:

   ```
   postgresql+psycopg://USER:PASSWORD@HOST/DB?sslmode=require
   ```

   Neon hands you `postgresql://…`. Without the `+psycopg` it will try to load
   `psycopg2`, which isn't installed, and startup fails.

Neon suspends when idle and drops open connections. `database.py` sets
`pool_pre_ping=True` and `pool_recycle=300` so a stale pooled connection is
detected and replaced instead of surfacing as an error.

## 2. API — Render

`backend/render.yaml` is a blueprint; point Render at the repo and it reads it.
Set the `sync: false` variables yourself:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Neon string from step 1 |
| `CORS_ORIGINS` | your Netlify URL, e.g. `https://valleylog.netlify.app` |
| `FRONTEND_BASE_URL` | same Netlify URL — used to build email verification links |
| `SMTP_USERNAME` / `SMTP_PASSWORD` | Gmail address + **app password**, not the account password |
| `SMTP_FROM_EMAIL` | the address verification mail is sent from |

`SECRET_KEY` is generated by Render. Don't rotate it casually — it signs the
JWTs, so changing it logs everyone out.

Schema creation is automatic: `main.py`'s lifespan runs `create_all()` and
`run_migrations()` on every boot, both of which are idempotent.

**Free tier:** the service sleeps after ~15 minutes idle and the next request
takes 30–60s to wake it. Data is unaffected because it lives in Neon.

## 3. Frontend — Netlify

Already configured by `netlify.toml` (base `frontend`, publish `dist`, SPA
rewrite). Add one environment variable:

| Variable | Value |
| --- | --- |
| `VITE_API_BASE_URL` | the Render URL, e.g. `https://valleylog-api.onrender.com` |

This is read at **build** time, not runtime — Vite inlines it into the bundle.
Setting it requires a redeploy to take effect. Without it the built app falls
back to `http://localhost:8000`, which in a visitor's browser means *their*
machine, so every API call fails.

## Moving existing data across

`backend/scripts/migrate_sqlite_to_postgres.py` copies the local SQLite database
into Postgres. It only ever reads the SQLite file.

```bash
cd backend
export TARGET_DATABASE_URL="postgresql+psycopg://…?sslmode=require"

python scripts/migrate_sqlite_to_postgres.py            # dry run, prints counts
python scripts/migrate_sqlite_to_postgres.py --write    # perform the copy
```

It refuses to write into a non-empty target. Rows keep their original ids so
foreign keys stay valid, and identity sequences are advanced afterwards —
without that the next signup would collide on a primary key.

Verified end-to-end against Postgres 16: 1 user, 3 villagers and 478
recipe-progress rows copied with no field-level differences, booleans and
timestamps converted correctly, and a subsequent signup allocating a fresh id.

## Local development is unchanged

With no `DATABASE_URL` set, `config.py` still defaults to
`sqlite:///./valleylog.db`, and the dialect-specific DDL in `run_migrations()`
resolves to the SQLite spellings.
